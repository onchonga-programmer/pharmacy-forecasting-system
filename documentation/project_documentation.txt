1. PROJECT OVERVIEW
================================================================================

This project builds a machine-learning-based demand forecasting system for
pharmacy sales data. The goal is to predict weekly drug sales quantities across
8 drug categories (identified by ATC codes), and to evaluate how well a trained
model generalises to future, unseen time periods.

The system implements and compares three classes of forecasting models:
  - Statistical baseline models (Naive, Seasonal Naive, SES, MA-4, WMA-4,
    Holt-Winters)
  - SARIMA (Seasonal AutoRegressive Integrated Moving Average)
  - XGBoost (gradient-boosted decision trees with engineered time-series
    features)

The final pipeline follows a strict 3-way temporal split:
  - TRAINING    : 2014 – 2017  (model learns from historical patterns)
  - VALIDATION  : 2018         (hyperparameter tuning and model selection)
  - FINAL TEST  : 2019         (out-of-sample generalisation test)

This design ensures no data leakage and provides an academically rigorous
evaluation of real-world model performance.

4. DATA CLEANING & PREPROCESSING
================================================================================

Notebook: notebooks/data_cleaning.ipynb

Steps performed:
  1. Loaded raw CSV (salesweekly.csv) into a pandas DataFrame
  2. Parsed and standardised the 'datum' (date) column to datetime format
  3. Renamed columns to English equivalents where needed
  4. Checked for and handled missing values
  5. Identified and handled outliers using IQR-based method (Cap)
  6. Reshaped data from wide format (one column per drug) to long format
     (drug_name column + quantity column) for modelling compatibility
  7. Saved two cleaned versions:
       - sales_cleaned.csv           (capped data, all years)
       - sales_cleaned_no_outliers.csv (outliers removed, all years)
  8. PIPELINE FORK — two separate modeling files are produced:

     SARIMA / Baseline branch (capped):
       sales_modeling_sarima.csv  — complete years, outliers capped at IQR
       Reason: SARIMA and Holt-Winters are linear models; extreme values
       directly bias their coefficient estimates and seasonal amplitudes.
       Capping prevents a few anomalous weeks from dominating the model.

     XGBoost branch (uncapped, raw values):
       sales_modeling_xgboost.csv — complete years, NO capping applied
       Reason: XGBoost is a tree ensemble. Trees learn split thresholds
       within the observed feature range. If training data is capped at
       (e.g.) 99.625, the model cannot predict values above that level at
       inference time — it cannot extrapolate beyond its training range.
       Training on raw uncapped data lets the model learn the full demand
       distribution (e.g., N02BE range 86–546 units/week).

     sales_modeling.csv — legacy alias, mirrors the SARIMA version for
       backward compatibility.

  This fork was implemented after the 2019 validation revealed that the
  original single-pipeline approach (capping applied to all models) caused
  catastrophic failure for N02BE: MAE 0.17 (artefact) → 121.39 in 2019.
  (See Bug 7 in Section 14 and the full explanation in Section 13.)

Output:
  - data/processed/sales_cleaned.csv
  - data/processed/sales_cleaned_no_outliers.csv
  - data/processed/sales_modeling_sarima.csv   ← SARIMA / Baseline input
  - data/processed/sales_modeling_xgboost.csv  ← XGBoost input (uncapped)
  - data/processed/sales_modeling.csv          ← legacy alias (= SARIMA file)

6. FEATURE ENGINEERING
================================================================================

Notebook: notebooks/pharmacy_sales_feature_engineering.ipynb

Input: data/processed/sales_modeling_xgboost.csv  (raw uncapped values)
  Note: The feature engineering notebook uses the XGBoost-specific file.
  This ensures that lag and rolling features are computed from the full
  uncapped demand range, matching what the model will see at inference time.
  SARIMA uses its own pre-split file (sales_modeling_sarima.csv) directly.

This notebook transforms the cleaned time-series data into a supervised machine
learning dataset with 47+ engineered features per observation.

Features created:

  TIME FEATURES:
    - month, quarter, week_of_year
    - month_sin, month_cos        — cyclical encoding for month
    - quarter_sin, quarter_cos    — cyclical encoding for quarter
    - week_sin, week_cos          — cyclical encoding for week of year
    - time_index                  — cumulative week count across all history
                                    (NOT reset per drug; counts from data start)

  LAG FEATURES (previous sales values):
    - lag_1   — previous week
    - lag_2   — 2 weeks ago
    - lag_4   — 1 month ago
    - lag_13  — 1 quarter ago
    - lag_52  — same week last year

  ROLLING WINDOW STATISTICS (computed per drug, no data leakage):
    Windows: 4, 13, 26, 52 weeks
    - rolling_mean_{w}
    - rolling_std_{w}
    - rolling_min_{w}
    - rolling_max_{w}

  EXPONENTIALLY WEIGHTED MOVING AVERAGES (EWM):
    - ewm_mean_4, ewm_mean_13, ewm_mean_26

  EXPANDING STATISTICS (computed using only historical data up to each point):
    - expanding_mean   — running mean of all past values
    - expanding_std    — running standard deviation
    Note: These are calculated using ALL available history (2014 onwards),
          ensuring no future leakage when applied in the 2019 test set.

  DRUG-LEVEL ENCODING:
    - drug_encoded     — integer label encoding of drug_name (sorted
                         alphabetically for reproducibility)
    - atc_main_group   — ATC main group encoding:
                           M (Musculo-skeletal) → 0
                           N (Nervous system)   → 1
                           R (Respiratory)      → 2
                         Note: Uses FIRST CHARACTER of ATC code, NOT full code

  DRUG STATISTICS (per-drug summary values from full training history):
    - drug_mean, drug_std, drug_min, drug_max, drug_cv

Data Split Applied in This Notebook:
  - All data up to 2017-12-31   → train sets  (train_xgboost.csv, etc.)
  - All data from 2018-01-01    → test sets   (test_xgboost.csv, etc.)
  - A label_encoders.pkl file is saved for reproducing encodings

Output files:
  - data/processed/train_xgboost.csv
  - data/processed/test_xgboost.csv
  - data/processed/train_sarima.csv
  - data/processed/test_sarima.csv
  - data/processed/train_baseline.csv
  - data/processed/test_baseline.csv
  - data/processed/label_encoders.pkl

7. TEMPORAL TRAIN / VALIDATE / TEST SPLIT STRATEGY
================================================================================

  ORIGINAL SPLIT (used for initial model development and leakage investigation):

  ┌────────────────────────────────────────────────────────────────┐
  │  PERIOD         │  YEARS     │  PURPOSE                       │
  ├─────────────────┼────────────┼────────────────────────────────┤
  │  Training Set   │ 2014–2017  │ Model learns demand patterns   │
  │  Validation Set │ 2018       │ Hyperparameter tuning, metrics │
  │  Test Set       │ 2019       │ Final out-of-sample evaluation │
  └─────────────────┴────────────┴────────────────────────────────┘

  PRODUCTION SPLIT (after retraining on extended dataset — see Section 18):

  ┌────────────────────────────────────────────────────────────────┐
  │  PERIOD         │  YEARS     │  PURPOSE                       │
  ├─────────────────┼────────────┼────────────────────────────────┤
  │  Training Set   │ 2014–2024  │ Model trained on full 10-year  │
  │                 │ (10 years) │ history (~523 weeks per drug)  │
  │  Test Set       │ 2025       │ Final out-of-sample evaluation │
  │                 │ (51 weeks) │ for the production webapp      │
  └─────────────────┴────────────┴────────────────────────────────┘

  Notes on the production split:
    - No separate validation year was used; hyperparameters were carried
      forward from the original 2018 validation experiments
    - SARIMA was evaluated on 2025 as a reference comparison but was
      excluded from the production webapp due to severe performance
      degradation (MAE=68.43 vs XGBoost=14.29; see Section 20)
    - The 2025 test set is entirely unseen data — no decisions about model
      architecture, features, or hyperparameters were made using 2025 data

Rationale:
  - Temporal splits are mandatory for time-series data to prevent data leakage
  - Using full calendar years (instead of random splits or rolling windows)
    ensures each split captures complete seasonal cycles
  - The 2019 test set is unseen during training AND validation — providing a
    true measure of real-world generalisation
  - 5 full years of training data is sufficient to learn weekly, monthly, and
    annual seasonal patterns
  - 2019 data is partial (Jan–Oct) but this is acceptable since all 4 seasons
    are represented across the full training history

This 3-way split applies to ALL models: baseline, SARIMA, and XGBoost.

11. MODEL VALIDATION — 2019 OUT-OF-SAMPLE TEST
================================================================================

Notebook: notebooks/model_validation_2019.ipynb

Purpose:
  To evaluate the trained XGBoost model (trained on 2014-2017, validated on
  2018) against completely unseen 2019 data. This is the final, definitive
  test of model generalisation.

How the 2019 test works:
  1. The 2019 weekly sales data is loaded and feature-engineered using the
     SAME transformations as training (lag features, rolling stats, etc.)
  2. Expanding stats use the FULL history (2014-2019) to avoid data leakage
  3. Drug encodings use the same sorted label encoder saved during training
  4. ATC main group encoding: M→0, N→1, R→2
  5. Features are passed to the saved XGBoost model for prediction
  6. Predictions are compared to actual 2019 values

Benchmark thresholds (dynamically computed):
  - Loaded from: data/results/xgboost/validation_2018_metrics.json
  - MAE threshold: dual — absolute MAE ≤ 3 units (PASS) / ≤ 10 units (WARN)
                   or relative change ≤ 20% (PASS) / ≤ 50% (WARN)
  - Prior versions used relative-only thresholds which incorrectly flagged
    low-error results when the baseline MAE was sub-unit (leakage artefact).

2019 Overall Results (all leakage fixed — clean model):
  Source: data/results/validation_2019/2019_predictions.csv

  Metric  | 2018 (Validation) | 2019 (Test) | Change
  --------+-------------------+-------------+----------
  MAE     |      11.45        |    12.48    |   +9.0%
  MAPE    |      25.55%       |    29.03%   |  +13.6%
  WMAPE   |      20.55%       |    24.02%   |    —
  R²      |       0.9189      |     0.8663  |   -5.7%

  Verdict: ✅ VALIDATION PASSED — 9% MAE degradation (within 20% threshold)

  ---
  RECOMMENDATION 4 IN DETAIL:
  Why XGBoost Should Be Retrained on Uncapped Data
  ---

  The data cleaning pipeline applied winsorization (outlier capping) before
  both SARIMA and XGBoost were trained. This was the right choice for SARIMA
  but the wrong choice for XGBoost, for fundamentally different reasons.

  Why capping was APPROPRIATE for SARIMA:
    SARIMA is a linear parametric model. It estimates additive components
    (trend, seasonal, error) by fitting coefficients to the observed series.
    A single extreme spike directly distorts those coefficient estimates —
    for example, one week where N02BE = 450 can inflate the seasonal
    coefficient for that calendar week across all future predictions.
    SARIMA has no built-in mechanism to discount individual extreme values.
    Winsorizing the training data before fitting SARIMA is therefore standard
    practice: it prevents a small number of anomalous weeks from biasing the
    model's understanding of "normal" seasonal demand.

  Why capping was HARMFUL for XGBoost:
    XGBoost is a tree-based ensemble model. Decision trees partition the
    feature space into rectangular regions by learning split thresholds
    (e.g., "if lag_1 > 180 then go right"). This means:

    (a) Trees are inherently robust to outliers in the TARGET variable.
        A large y-value does not distort splits — it simply becomes a leaf
        node with a high predicted value. Unlike linear models, XGBoost does
        not need the target to be bounded in order to produce stable estimates.

    (b) Trees REQUIRE the training and inference feature distributions to
        match. If the model is trained on data where lag_1 ≤ 99.625, it will
        have learned splits only within that range (e.g., "lag_1 > 97" or
        "lag_1 > 95"). When presented with lag_1 = 289 at inference time,
        every split threshold it learned is below that value, so the input
        falls into the rightmost leaf of every tree — a leaf that was only
        ever trained on values ≈ 99. The model cannot extrapolate; it returns
        its highest-seen prediction (~71 units) rather than anything near the
        true value of ~354.

    (c) Capping destroyed real signal. N02BE's raw range is 86–546 units/week.
        Capping at 99.625 compressed 68% of the actual demand range into a
        single boundary value. The model never learned that demand can be 200,
        300, or 500 units/week, nor what feature patterns (e.g., high lagged
        values, seasonality, trend) correspond to those high-demand periods.
        If retrained on uncapped data, XGBoost would learn splits such as:
          "if lag_1 > 200 AND month_sin > 0.8 → predict 380"
        which would be far more useful for real-world pharmacy restocking.

  The right approach for XGBoost:
    Option A — Train on raw uncapped data (recommended):
      Remove the winsorization step from the XGBoost branch of the pipeline.
      XGBoost's gradient boosting objective is robust to large values because
      individual trees are shallow (max_depth=5–6) and the learning rate
      shrinks each tree's contribution. The ensemble averages out any single
      tree overfit to an extreme value.
      Expected outcome: the model correctly learns the N02BE high-demand
      regime (lag_1 ≥ 200 → high predicted sales), and 2019 MAE is expected
      to fall sharply from 121.39 to a level comparable to other drugs.

    Option B — Apply log transformation instead of capping:
      Replace winsorization with log1p(x) = log(1 + x) on total_quantity.
      This compresses the tail (reducing the influence of extreme values)
      without destroying information the way hard capping does.
      The full range 86–546 maps to 4.46–6.30 in log space — a modest
      ratio of 1.41×, versus a raw ratio of 6.3×. XGBoost can learn this
      compressed range easily and predictions are back-transformed with
      expm1(). This is a common best-practice for count/sales data.

    Option C — Keep capping but apply it consistently (minimal fix):
      As implemented in the Bug 7 fix, apply the same training-time cap to
      all inference inputs. This prevents the out-of-distribution failure
      but does NOT fix the underlying limitation: the model still cannot
      predict demand above 99.625 for N02BE, which is wrong for 2019.
      This option is only suitable as a short-term patch.

  Summary for write-up:
    Outlier capping is a preprocessing step that must be tailored to the
    model type, not applied uniformly across all models in the pipeline.
    SARIMA benefits from capping because it is a linear model sensitive to
    leverage points. XGBoost does not benefit from capping — it is harmed
    by it, because trees cannot extrapolate beyond the range of values they
    were trained on. The correct preprocessing strategy for a tree ensemble
    on pharmaceutical sales data is either to use raw counts directly or to
    apply a variance-stabilising transformation (log/sqrt) that preserves
    the ordering and relative magnitude of all demand levels.

14. BUGS FOUND & FIXED DURING DEVELOPMENT
================================================================================

The following technical issues were identified and resolved during development:

  Bug 1: Feature Column Order Mismatch
    - Problem : XGBoost model expected features in a specific column order.
                Running model_validation_2019.ipynb produced a
                "feature_names mismatch" error.
    - Fix     : Reordered the 2019 feature DataFrame to match the exact
                column sequence used during model training using
                feature_cols_ordered.

  Bug 2: time_index Computed Incorrectly in 2019 Notebook
    - Problem : time_index was computed as range(len(df_2019)), which reset
                the counter to 0 for 2019. The model expected a cumulative
                index counting from 2014.
    - Fix     : Changed to compute time_index as cumulative week count from
                the start of the full dataset (2014 onwards).

  Bug 3: Expanding Stats Computed Only on 2019 Data
    - Problem : expanding_mean and expanding_std were calculated using only
                the 2019 slice of data. This gave wrong values and was a
                form of data inconsistency.
    - Fix     : Recalculated expanding stats using the full 2014-2019 history
                concatenated, then selected 2019 rows after computation.

  Bug 4: ATC Encoding Used Full Codes Instead of Main Group
    - Problem : During 2019 re-encoding, the full ATC code (e.g., 'M01AB')
                was mapped instead of the main group initial character ('M').
                This caused the model to receive encoding values it had never
                seen during training.
    - Fix     : Applied .str[0] to extract the first character of the ATC
                code before mapping to the integer encoding (M→0, N→1, R→2).

  Bug 5: Drug Label Encoding Not Reproducible
    - Problem : Drug integer encoding used an unsorted list of drug names,
                meaning the mapping could vary between runs depending on the
                order data appeared.
    - Fix     : Enforced sorted(df['drug_name'].unique()) to ensure the
                encoding is always alphabetically consistent.

  Bug 6: Hardcoded 2018 Benchmark Values Became Stale
    - Problem : model_validation_2019.ipynb had hardcoded 2018 metrics
                (MAE=1.40, per-drug MAEs) from an earlier training run.
                After retraining on 2014-2017, the actual 2018 results
                changed to MAE=1.81 — making all comparisons incorrect.
    - Fix     : Replaced all hardcoded values with dynamic loading from:
                  - validation_2018_metrics.json  (overall metrics)
                  - xgboost_results.csv           (per-drug metrics)
                All thresholds (e.g., MAE < 2.17) are now computed at
                runtime as mae_2018 × 1.20.

  Bug 7: Training Outlier Cap Not Applied to 2019 Inference Pipeline
    - Problem : The data cleaning pipeline winsorized (capped) sales
                quantities per drug to remove outliers before training.
                For N02BE, this cap was 99.625 units/week. In the 2018
                test split, ALL N02BE values were exactly 99.625 (constant).
                The model learned to predict ≈ 99.625 for N02BE — giving
                an artefactual MAE of 0.17 (near-zero error on a constant).

                In model_validation_2019.ipynb, the 2019 data was loaded
                directly from the database (raw, uncapped values up to 546)
                and lag features were computed from this raw history
                (lag_1 = 289 instead of ≤ 99.625). These values were
                completely out-of-distribution for the trained model,
                causing predictions of ≈ 71 against actuals of ≈ 354,
                producing MAE = 121.39.

    - Confirmed by:
                  • train_xgboost.csv N02BE range: 92.0 – 99.625
                  • test_xgboost.csv  N02BE range: 99.625 – 99.625 (constant)
                  • Database 2019 N02BE range    : 86 – 546 (raw)
                  • Encoding sensitivity test: prediction unchanged across
                    all drug_name_encoded values (0–7) → encoding not the cause
                  • lag_1 mismatch confirmed: stored 289.0, expected ≤ 99.625

    - Fix     : In model_validation_2019.ipynb (debug section):
                  1. Learn per-drug caps from train_xgboost.csv
                  2. Apply caps to df_full before computing lag/rolling features
                  3. Apply caps to df_2019 actuals for fair comparison
                  4. Rebuild all lag/rolling/EWM features from capped history
                  5. Re-score with corrected feature matrix

    - Lesson 1: Any preprocessing step applied during training (scaling,
                capping, encoding) MUST be reproduced identically during
                inference. Saving the cap values alongside the model
                (e.g., in a preprocessing_config.json) is recommended
                for all future pipelines.

    - Lesson 2: Outlier capping is model-type-dependent and must NOT be
                applied uniformly across all models in a pipeline.

                SARIMA  → capping HELPS.
                  SARIMA is a linear parametric model. Extreme values directly
                  bias its coefficient estimates (trend slope, seasonal
                  amplitudes). Removing or capping spikes before fitting
                  prevents a handful of anomalous weeks from dominating the
                  model's representation of normal seasonal behaviour.

                XGBoost → capping HURTS.
                  XGBoost is a tree ensemble. Decision trees learn split
                  thresholds within the observed feature range. If every
                  training example has lag_1 ≤ 99.625, the model learns splits
                  only within [0, 99.625]. At inference time, an input of
                  lag_1 = 289 falls beyond all learned thresholds and maps to
                  the same extreme leaf as lag_1 = 99 — the model cannot
                  distinguish the two. This is not overfitting; it is the
                  fundamental inability of a tree to extrapolate outside its
                  training range.

                  Furthermore, tree ensembles are inherently robust to large
                  target values: a week with sales=450 simply becomes a leaf
                  with a high predicted value; it does not skew the splits of
                  other leaves. Capping is therefore both unnecessary and
                  counterproductive for XGBoost.

                  The correct fix for XGBoost is to train on uncapped data
                  (or log-transformed data), so the model learns the full
                  demand distribution and can make valid predictions across
                  the observed range at inference time.

  Bug 8: Data Leakage in Trend and Statistical Features
    - Problem : Three feature engineering steps used the actual target
                value at time t instead of the lagged value at t-1:

                  diff_1w = actual[t] - actual[t-1]       ← leaks actual[t]
                  pct_change_1w = diff_1w / actual[t-1]   ← leaks actual[t]
                  ratio_to_expanding_mean = actual[t] /
                    expanding_mean_to_t-1                 ← leaks actual[t]

                This is target leakage — the feature directly encodes
                information about the value being predicted, making the
                model appear far more accurate than it actually is.

    - Confirmed by: R²=1.00 for 7/8 drugs (impossible without leakage)
    - Fix     : All three formulas replaced with lag-based equivalents:
                  diff_1w = lag_1 - lag_2
                  pct_change_1w = (lag_1 - lag_2) / lag_2
                  ratio_to_expanding_mean = lag_1 / expanding_mean

                Applied in:
                  - notebooks/pharmacy_sales_feature_engineering.ipynb
                    (cell: Trend features — diff, pct_change, ratio)
                  - notebooks/model_validation_2019.ipynb
                    (cell: trend features)

    - Lesson  : Any feature that divides, subtracts, or compares the
                raw target variable against a lagged/aggregate statistic
                must use the LAGGED target (t-1 or earlier), never the
                current target (t).

  Bug 9: drug_avg_sales Computed on Full Dataset Including Test Period
    - Problem : The drug-specific statistical features (drug_avg_sales,
                drug_std_sales, drug_min_sales, drug_max_sales, drug_cv)
                were computed from the entire dataframe (all years 2014-2018),
                including the 2018 test period.

                  # Bug:
                  drug_level_stats = df_model.groupby('drug_name')['total_quantity'].agg(...)

                This means the 2018 test rows contributed to the mean
                and standard deviation that the model used as features —
                a subtle form of future leakage.

    - Fix     : Drug statistics are now computed exclusively from the
                training data (years 2014-2017):

                  # Fix:
                  drug_level_stats = train_xgb.groupby('drug_name')['total_quantity'].agg(...)

                Applied in:
                  - notebooks/pharmacy_sales_feature_engineering.ipynb
                    (cell: Drug-specific features)
                  - notebooks/model_validation_2019.ipynb
                    (drug stats computed from df_full[year < 2019])

    - Lesson  : Any aggregate statistic used as a feature (mean, std, etc.)
                must be computed from training-period data only, never
                from the full dataset. This applies to group statistics,
                global statistics, and any normalization reference values.

  Bug 10: total_quantity_log (Log of Target) Included as Feature
    - Problem : The feature engineering pipeline created a
                total_quantity_log = log1p(total_quantity) column and
                stored it in the training/test CSVs alongside all other
                features. In the XGBoost model notebook, the metadata_cols
                exclusion list contained total_quantity_scaled but NOT
                total_quantity_log. Therefore, log(target) was included
                in the feature matrix passed to XGBoost.

                log1p(total_quantity) is a monotonic transformation of
                the target — it IS the target in disguise. Including it
                as a feature is direct target leakage: the model can
                perfectly reconstruct the target from this single feature.

    - Confirmed by: Adding total_quantity_log to metadata_cols caused
                    feature count to drop from 48 to 47, and 2018 MAE
                    increased from 0.14 to 11.45 (realistic).

    - Fix     : Added 'total_quantity_log' to metadata_cols in:
                  - notebooks/pharmacy_xgboost_model.ipynb
                    (cell: Data loading and feature setup)
                  - notebooks/model_validation_2019.ipynb
                    (cell: Feature column preparation)

                  metadata_cols = [..., 'total_quantity_log',
                                        'total_quantity_scaled']

    - Lesson  : Any column derived from the target variable
                (log, sqrt, standardised, binned, etc.) must be
                explicitly excluded from the feature matrix. The safest
                approach is a whitelist of allowed features rather than
                a blacklist of excluded ones.

  Impact of Bug 8-10 Fixes (cumulative effect):
    Before all fixes:  2018 MAE=0.14, R²=0.9999 (near-perfect, impossible)
    After Bug 8 fix:   2018 MAE=0.14, R²=0.9999 (still wrong — log leakage)
    After Bug 9 fix:   drug stats are clean but log leakage persists
    After Bug 10 fix:  2018 MAE=11.45, R²=0.9189 (realistic, honest)
    2019 final test:   MAE=12.48, R²=0.8663 (+9% degradation — PASS)

17. KEY CONCLUSIONS
================================================================================

1. XGBoost and Holt-Winters Both Perform Strongly on Extended Dataset
   After retraining on the full 2014–2024 dataset (10 years), both models
   achieved R² > 0.87 on the unseen 2025 test set:
     - XGBoost     : MAE=14.29, R²=0.8774, WMAPE=25.11%
     - Holt-Winters: MAE=13.11, R²=0.8928, WMAPE=23.02%
   Holt-Winters leads on all primary metrics (MAE, RMSE, WMAPE, R²) in 2025.
   Both models generalise well to a fully unseen calendar year.
   A per-drug hybrid approach is deployed in the production webapp: XGBoost
   is the primary model; Holt-Winters is used automatically for N05C and N02BA
   (low-volume, irregular demand drugs).

   NOTE: Original 2018 results (MAE=11.45) were derived from a 4-year training
   set. After retraining on 10 years, the production model is now evaluated
   on 2025 data. The earlier 2018/2019 results remain valid as an academic
   record of model development and leakage debugging.

2. 2019 Validation Passed With Minimal Degradation (Original Pipeline)
   The original out-of-sample test (2019) showed only +9.0% MAE degradation
   (11.45 → 12.48), R²=0.8663. This confirmed the model generalises to future
   data before the decision was made to retrain on extended data.
   Earlier versions of the pipeline showed VALIDATION FAILED (+932% MAE);
   this was caused by data leakage and an inconsistent inference pipeline
   (Bugs 7-10).

3. Data Leakage Is The Primary Threat to Model Integrity
   Four distinct leakage bugs were identified and fixed during development:
   - Bug 7 : Training outlier cap not applied at inference → OOD features
   - Bug 8 : Trend features using actual[t] instead of lag[t-1]
   - Bug 9 : Drug-level statistics computed from full dataset (incl. test)
   - Bug 10: total_quantity_log (= log of target) included as a feature

   The combined effect caused reported 2018 MAE to drop from a true value
   of 11.45 to an artefactual 0.14 — a 99% artificial improvement.
   This underscores that data leakage detection must be an explicit, systematic
   step in every supervised learning pipeline, particularly for time-series
   forecasting where chronological structure makes leakage easy to introduce.

4. Model Retraining Confirmed Real-World Viability
   After retraining on 10 years of data (2014–2024) and testing on 2025:
     XGBoost: MAE=14.29, R²=0.8774 | Holt-Winters: MAE=13.11, R²=0.8928
   Both models remain strong predictors on fully unseen future data.
   Quarterly 2025 analysis shows consistent performance across all four
   quarters (Q1 MAE=15.67, Q2=13.62, Q3=13.22, Q4=14.69 for XGBoost)
   — substantially more stable than the original 2019 test, where Q1
   suffered from a post-holiday N02BE spike (Q1 MAE=16.60, Q4=35.62).
   The enlarged training set better captures long-term demand seasonality.

5. Feature Engineering Proved Critical
   The rich feature set (lags, rolling stats, EWM, cyclical encodings, expanding
   stats, drug-level statistics) was key to XGBoost's strong performance and
   R²=0.8774 on the 2025 out-of-sample test. All 47 features are derived
   from information available strictly before the prediction point.

6. Temporal Validation is Essential for Time-Series Models
   Using strict temporal splits (no random shuffling) and an independent
   held-out years (2019, then 2025) prevented overfitting and produced
   honest, academically rigorous results. Neither test year was visible
   during model design or hyperparameter selection.

7. Preprocessing Must Be Tailored Per Model, Not Applied Uniformly
   The project uses two separate preprocessing pipelines:
     - sales_modeling_sarima.csv  (IQR-capped) for SARIMA and Holt-Winters
     - sales_modeling_xgboost.csv (uncapped)   for XGBoost
   SARIMA and Holt-Winters are linear models that benefit from outlier capping.
   XGBoost is a tree ensemble that requires the full demand range in training
   — it cannot extrapolate beyond its training range. Applying the same
   capping to XGBoost caused the N02BE OOD failure (Bug 7).

8. Honest Model Assessment Requires Systematic Leakage Auditing
   This project identified four successive leakage bugs, each of which
   was masked by the ones that came before it. A formal leakage audit
   checklist — covering feature computation order, group statistics scope,
   target-derived features, and inference pipeline consistency — should be
   applied to every supervised forecasting project before reporting results.

9. SARIMA Is Unsuitable for This Dataset at Weekly Granularity
   After evaluating SARIMA on the 2025 test set (MAE=68.43, R²=−2.69),
   SARIMA was removed from the production webapp entirely. It was worse
   than a naive mean predictor (R²<0) for all quarters and all drugs.
   The root cause is insufficient training data for a seasonal period of
   s=52: even with 10 years of training data, SARIMA's AIC-selected orders
   produced degenerate or near-trivial models for most drugs. Holt-Winters
   (the simplest exponential smoothing variant) consistently outperforms
   SARIMA at this data granularity and frequency.

10. The Production System Deploys a Pharmacist-Friendly Web Interface
    A Django 4.x webapp presents all forecasting results in plain language
    accessible to clinicians with no data-science background. Key design
    decisions: all ML jargon replaced with plain-English equivalents;
    problematic drugs sorted to the top of every table; every flagged drug
    shows a visible "Next Step" action; advanced metrics hidden behind a
    "Show advanced data" toggle; threshold reference lines on all charts.

18. XGBOOST RETRAINING — EXTENDED DATASET (2014–2024)
================================================================================

Motivation:
  The initial model development cycle (Sections 8–13) used a training period
  of 2014–2017 (4 years). After all data leakage bugs were identified and
  fixed, the final clean 2019 test result was MAE=12.48 (+9% from the 2018
  validation). While this passed the 20% degradation threshold, the training
  history was deliberately limited to maintain a clean academic split.

  Once the academic pipeline was complete, the decision was made to retrain
  on the maximum available history (2014–2024) for production deployment.
  Using 10 full years of weekly data:
    - Captures a broader range of seasonal, trend, and demand-shift patterns
    - Provides more stable lag and rolling feature statistics
    - Reduces the influence of any single unusual year (e.g., post-COVID)
    - Enables more reliable long-range lag features (lag_52 is valid for
      all training rows after the first year, instead of only for rows
      after 2015)

Training Configuration (Production Retrain):
  - Training period  : 2014–2024 (all available completed years)
  - Test period      : 2025 (full calendar year, 51 weeks per drug, 408 total)
  - Algorithm        : XGBoost Regressor (same architecture as original)
  - Features         : Same 47 engineered features (see Section 6)
  - Hyperparameters  : Carried forward from 2018 grid-search experiments
                       (max_depth=3, learning_rate=0.1, n_estimators=100,
                        subsample=1.0, colsample_bytree=1.0)
  - No separate held-out validation year; hyperparameters were frozen from
    the original experiments to avoid any 2025 data snooping

Output Files:
  - data/results/xgboost/xgboost_final_model.pkl  (overwritten)
  - data/results/xgboost/xgboost_model.json       (overwritten)
  - data/results/xgboost/validation_metrics.json  (train: 2014-2024, val: 2025)
  - data/results/xgboost/xgboost_results.csv      (2025 per-drug XGBoost metrics)
  - data/results/xgboost/feature_importance.csv   (updated)
  - data/results/xgboost/best_params.pkl          (updated)

  The original validation_2018_metrics.json is retained for reference only.

Holt-Winters Retraining:
  Holt-Winters does not use a saved model file. It is fitted at inference time
  (in ml_engine.py) on ALL historical data available up to the forecast date.
  After the data extension, the HW model automatically benefits from 10 years
  of training history without any code changes.

Seasonal Naive / Baseline Comparison:
  Baseline models were not formally rerun against 2025 data. The 2025 test
  serves as the production model evaluation, not a model-selection exercise.

20. SARIMA REMOVAL FROM PRODUCTION SYSTEM
================================================================================

Decision Date : March 2026
Reason        : Unacceptable performance on 2025 out-of-sample test

SARIMA 2025 Test Results:
  MAE=68.43 (vs XGBoost 14.29 — 4.8× worse)
  RMSE=136.38 (vs XGBoost 24.85 — 5.5× worse)
  R²=−2.693 (negative — worse than predicting the mean in all cases)
  WMAPE=120.2% (vs XGBoost 25.11%)

Per-Drug SARIMA MAE vs XGBoost MAE (2025):

  Drug   | SARIMA MAE | XGB MAE | Ratio (SAR/XGB)
  -------+------------+---------+----------------
  N02BE  |   212.78   |  48.89  |    4.4×
  N05B   |   123.07   |  15.17  |    8.1×
  R03    |    83.10   |  20.98  |    4.0×
  R06    |    33.97   |   8.95  |    3.8×
  M01AB  |    49.10   |   7.91  |    6.2×
  M01AE  |    35.19   |   4.84  |    7.3×
  N02BA  |     5.92   |   5.19  |    1.1×  (closest, still worse)
  N05C   |     4.28   |   2.41  |    1.8×

  SARIMA is worse than XGBoost for every single drug on 2025 data.
  It is better than XGBoost on 0/8 drugs.

Root Cause Analysis:
  SARIMA at weekly granularity (s=52) requires at minimum 3–5 full seasonal
  cycles in the training data to reliably estimate seasonal parameters.
  Even with 10 years of training data (2014–2024), the AIC-selected SARIMA
  orders produce near-trivial models for high-volume volatile drugs
  (N02BE, N05B, R03) where the seasonal signal is dominated by random
  demand variation.

  Additionally, SARIMA is a univariate model — it cannot use the rich set
  of engineered features (lag patterns, rolling statistics, drug-level
  encodings) that allow XGBoost and Holt-Winters to capture cross-drug
  demand patterns and long-term trends.

Files Removed from Webapp:
  All SARIMA-specific template variables, model badges, and result displays
  were removed from the Django webapp (templates and views.py) in February 2026.
  SARIMA result files (data/results/sarima/) are retained as academic records.

Impact on Webapp:
  - Forecast page: "SARIMA" model badge replaced with "Automated Forecast"
    (XGBoost primary) or "Backup System Active" (Holt-Winters)
  - Results page: SARIMA comparison column removed; only XGBoost vs
    Holt-Winters comparison is shown
  - Dashboard / Drift pages: Only XGBoost and HW error bars displayed
