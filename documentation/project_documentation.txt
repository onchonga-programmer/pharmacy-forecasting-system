PHARMACY FORECASTING SYSTEM - PROJECT DOCUMENTATION
Updated: 30 March 2026

======================================================================
1. PROJECT PURPOSE
======================================================================
This project forecasts weekly pharmacy demand for 8 ATC drug categories to
support stock planning and reduce stockouts/overstock.

The final system combines data science outputs (model training + validation)
with a Django web application used by end users.

Drug categories:
M01AB, M01AE, N02BA, N02BE, N05B, N05C, R03, R06


======================================================================
2. DATA AND TRAINING WINDOW
======================================================================
Source dataset:
- data/raw/salesweekly.csv

Modeling datasets used by the application:
- data/processed/sales_modeling.csv
- data/processed/sales_modeling_xgboost.csv
- data/processed/sales_modeling_sarima.csv

Final temporal split used for production-level validation:
- Training period: 2014-2024
- Validation/Test period: 2025 (fully out-of-sample)

Why this split was used:
1. It preserves chronological order and avoids data leakage.
2. It simulates real deployment conditions (forecasting future unseen weeks).
3. It provides a strong test of model robustness across seasonal and demand
   variability over a full calendar year.

3. MODELS TRAINED AND EVALUATED
======================================================================
Three model families were compared:

A) BASELINE STATISTICAL MODELS
- Naive, Seasonal Naive, SES, moving average variants, Holt-Winters.
- Baseline summary files:
  - data/results/baseline_models/baseline_summary.csv
  - data/results/baseline_models/best_baseline_model.txt

B) SARIMA
- Per-drug SARIMA models with seasonal structure.
- Result file:
  - data/results/sarima/sarima_results.csv

C) XGBOOST
- Supervised model trained on engineered lag, rolling, trend, seasonal,
  and encoded category features.
- Main output files:
  - data/results/xgboost/xgboost_model.json
  - data/results/xgboost/xgboost_final_model.pkl
  - data/results/xgboost/validation_metrics.json

5. MODELS CHOSEN AND WHY
======================================================================
Final practical model strategy in the system is hybrid, not single-model.

Chosen for deployment:
1. XGBoost as the primary forecasting engine for most drugs.
2. Holt-Winters as backup and preferred model for selected irregular/low-volume
   drugs (currently N05C and N02BA in the webapp engine).

Not chosen for deployment:
- SARIMA, due to very poor out-of-sample performance in 2025 (large errors and
  strongly negative R2 across many drugs).

Why XGBoost remained in the deployed workflow:
1. Strong overall generalization on 2025 (R2 about 0.88).
2. Handles rich engineered features and nonlinear interactions.
3. Already integrated as the main model artifact in the web app pipeline.
4. Supports robust fallback logic when feature/history conditions fail.

Why Holt-Winters is included as backup/secondary model:
1. Best MAE in the 2025 benchmark table.
2. Stable for some low-volume or irregular-demand series.
3. Simple and reliable for one-step and short-horizon operational forecasts.

Why SARIMA was removed from production path:
1. Very high error magnitudes in 2025.
2. Unreliable generalization (negative R2).
3. Inferior performance versus both XGBoost and Holt-Winters.

6. WEBAPP INTEGRATION (DJANGO)
======================================================================
Web application location:
- webapp/

Main forecasting integration file:
- webapp/forecasting/ml_engine.py

How integration works:
1. Path wiring in ml_engine.py points from webapp to project-level data/results
   directories.
2. The engine loads persisted artifacts and evaluation files, including:
   - xgboost_final_model.pkl
   - validation_2025 metrics and prediction tables
3. Forecast requests call generate_forecast(), which uses model-routing logic:
   - Route selected drugs to Holt-Winters directly (N05C, N02BA).
   - Otherwise run XGBoost.
   - If XGBoost fails, automatic fallback to Holt-Winters.
4. Confidence intervals are built from per-drug MAE and confidence tiers.
5. Batch CSV forecasting is supported through process_csv_forecast().
6. Inventory recommendations are computed from demand statistics in
   compute_inventory_recommendation().

Django endpoint mapping:
- webapp/forecasting/urls.py
  - /            -> dashboard
  - /results/    -> model comparison and per-drug performance view
  - /forecast/   -> single and batch forecast interface
  - /drift/      -> drift/performance monitoring dashboard
  - /inventory/  -> inventory decision support

Project URL mount:
- webapp/pharmacy_system/urls.py
  - root path includes forecasting.urls

View-layer integration:
- webapp/forecasting/views.py
  - Reads model metrics and prediction files via ml_engine helpers.
  - Builds charts (Plotly) for dashboard, results, forecast, and drift pages.
  - Displays primary vs backup model behavior using 2025 metrics.


======================================================================
7. TRAINING-TO-DEPLOYMENT PIPELINE SUMMARY
======================================================================
1. Prepare cleaned and modeling datasets from raw weekly sales.
2. Train and evaluate baseline, SARIMA, and XGBoost families.
3. Retrain/finalize with history through 2024.
4. Validate on full unseen 2025 period.
5. Select deployment strategy based on out-of-sample behavior.
6. Integrate selected models into Django forecasting engine.
7. Expose operational dashboards and forecasting workflows to users.


======================================================================
8. KEY CONCLUSIONS
======================================================================
1. The project used a valid temporal experiment design: train on 2014-2024,
   test on unseen 2025.
2. SARIMA underperformed and was not suitable for production use.
3. XGBoost and Holt-Winters were the practical models retained.
4. The deployed system uses a hybrid route-and-fallback strategy to improve
   reliability at inference time.
5. The webapp is fully integrated with model files, validation artifacts,
   visual dashboards, and inventory-support logic.
